## 6. 经验总结

### 6.1 做得好的地方

1. **原型驱动把需求"钉死"在编码之前。** M2 阶段对 P01 ~ P10 共十个页面逐页走查，业务方在 SRS 7.2 十步演示脚本上确认闭环后才开工。结果是编码阶段**没有发生一次因需求理解偏差导致的返工**，4 项变更中 2 项被驳回或延期，验证了高风险项 R-01 应对策略的有效性。
2. **业务规则集中配置带来了真实的可维护收益。** 审批阈值（15% / 30% / 100 万）、阶段赢率、客户等级阈值、分期模板全部集中在 `src/config/businessRules.ts`（仅 148 行）。CR-001 将审批扩展为两级时只改配置与审批链生成器；BUG-003（15% 边界判定错误）只修一处即全链路生效，"禁止硬编码"真正降低了变更成本。
3. **需求追踪矩阵保证了"无遗漏"。** 需求 → 用例 → 设计 → 测试用例的追溯链在 M5 前做过双向孤儿检查：54 条功能需求与 20 条关键非功能需求全部有对应用例，无孤立设计项，使"每个需求都被验证过"成为可举证的事实。
4. **增量交付消解了"末期才见成品"的风险。** v0.5.0 即跑通 L2C 主干，v0.9.0 补齐看板拖拽与系统管理，使 M4 ~ M6 连续提前；即使增量被裁剪，核心流程仍可完整演示。
5. **边界值驱动的用例设计投入产出比最高。** R1 ~ R4 的五条边界用例一次执行即发现 2 条主要缺陷（BUG-002、BUG-003）；线索批量分配 3 条与 51 条、客户等级双阈值同理，投入产出比远超"遍历式"用例。
6. **金额整数分存储从源头消灭了浮点误差。** SRS 2.5 的这条约束贯穿到实现层，避免了回款汇总、进度百分比、客户等级评定三处口径漂移。
7. **受控的变更机制守住了范围。** CR-002（+28 人日）与 CR-004（+9 人日）在 CCB 环节被分别"驳回"与"延期"，且都给出了业务方可接受的替代方案，证明流程不是拖慢效率而是防止返工。

### 6.2 不足与教训

1. **前期需求调研对异常场景挖掘不够。** 12 条缺陷中有 6 条的根因是"校验或异常分支未处理"（溢收、跨期归集、过期报价、重名转化等）。访谈基本围绕正常流程展开，很少问到"如果登记金额超过剩余应收怎么办"，导致缺陷全部推迟到测试阶段才暴露。
2. **测试用例编写滞后于开发。** 用例集中设计于 2026-10-04 ~ 10-07，编码自 10-02 已启动，两者并行却不同步。结果是缺陷在执行首日集中爆发（10 条），第二轮回归又冒出 2 条，"测试左移"只落实到纸面而未落实到排期。
3. **完全没有自动化测试。** 107 条用例全部手工执行，4 轮回归耗时约 14 小时，每次改代码都要重跑人工验证。尤其 `businessRules.ts` 与 `selectors.ts` 这类最易自动化的纯函数竟无一条单元测试，这是本期质量资产上最大的亏空。
4. **LocalStorage 持久化方案的局限性被低估。** 压力测试因"构造脚本注入失败（写入超容量）"而阻塞，导致 NFR-P-04（单表 10000 条）至今未验证；此外还带来数据无法跨端共享、清理缓存即丢失、演示数据与真实数据混杂三个问题。选型时只论证了"能跑通闭环"，没论证"能承载多大数据"。
5. **代码度量未达标却未及时纠偏。** NFR-M-04 要求单文件 ≤300 行，实际 8 个文件超限，`AppContext.tsx` 达 762 行。评审发现了问题却以"拆分会破坏语义集中"为由放行，只登记了一个待重构项（D-01）。约束一旦可被随意豁免，规范就失去意义。
6. **五条缺陷源于"校验函数已实现但调用点未接入"。** BUG-002、BUG-006 ~ BUG-009 的共同根因是同一校验逻辑在不同页面被各自调用或漏调，说明"收敛为单一入口"的原则在编码压力下未被坚持。
7. **配置管理执行不到位。** Git 仓库仅完成初始化，**提交数为 0、tag 数为 0**，分支策略与提交规范写进文档却从未真正执行，导致无法用提交日志佐证过程数据，也无法回退版本。这是本期最严重的流程性欠账（L-01）。
8. **浏览器兼容性验证前置不足。** Firefox 下的图表渲染问题（BUG-012）在验收前一天才被发现，暴露了"只在主用浏览器上开发和自测"的习惯。
9. **文档间的定量口径未统一校准。** 《里程碑与版本规划》中的"286 条用例 / 97.6%"与《测试报告》的"107 条 / 96.26%"不一致；个别文档交叉引用的编号与磁盘上的实际编号亦有出入。多人编写却缺少一次集中交叉校验（L-08）。

### 6.3 如果重做，我会这样改进

1. **建立"异常分支清单"作为需求评审的强制检查项。** 每条功能需求除正常流程外，必须显式列出金额超限、重复提交、跨期归集、权限不足、数据过期、写入失败六类异常的处理方式并直接落成用例。三分之一的缺陷源于"异常分支没想清楚"，这是本期最贵的教训。
2. **让用例与设计同步冻结，把测试真正左移。** 详细设计评审通过即冻结用例骨架（含边界值表），用例不再是测试阶段的产物，编码完成后只做补充与执行。
3. **引入自动化回归，先覆盖纯函数。** 重做时第一件事就是为 `businessRules.ts` 与 `selectors.ts` 编写 Vitest 单元测试（目标覆盖率 ≥80%），再把 5 条端到端主路径与 R1 ~ R4 边界集固化为每次发布强制执行的 P0 回归集。这两类资产只需额外约 2 人日，却能在后续每个版本节省数倍回归成本。
4. **持久化选型提前做容量验证。** 选型阶段即用脚本注入 10000 条数据验证容量上限，或采用 IndexedDB + Repository 双实现，并明确"演示数据"与"用户数据"分区存储。
5. **把 Git 规范变成门禁而非纸面条款。** 强制提交关联 WBS 或需求编号、提交前自动执行静态检查与类型检查、每次发布必打附注 tag，并把"是否形成提交历史"作为里程碑准入的硬条件。
6. **建立文档数据的单一事实来源。** 用例数、缺陷数、工作量与版本信息统一登记在一张基线数据表中，其余文档引用而非复写，发布前用交叉校验清单收口一次。

## 8. 课程学习收获

| 知识模块 | 真实体会 |
|---|---|
| **需求工程** | 以前以为"需求就是用户说的话"，做完才明白需求是一份需要论证、编号、评级、基线化和受控的工程资产。标注优先级与验收标准后，"做完了没有"才成为可判定的问题。最大的教训是：需求不仅要写清"正常怎么做"，更要写清"异常怎么办"。 |
| **建模方法** | 用例模型解决"谁做什么"，状态机解决"对象能变到哪去"，数据模型解决"怎么存"，决策表解决"复杂条件怎么判定"。商机五阶段状态机是 FR-05 七条需求的骨架，R1 ~ R4 决策表让原本需大段文字描述的审批逻辑变成四条可验证规则，边界用例照表即可列出。 |
| **原型验证** | 原型不是效果图，而是需求确认的工具。M2 阶段让业务代表在十个页面上逐页走查端到端场景，当场暴露三处流程分歧并在编码前修正；没有这一步，这些分歧会在编码完成后才被发现，成本至少增加十倍。同时也学到原型的边界：静态原型不承担数据校验，须由可运行版本接力。 |
| **配置管理** | 这一项我们做砸了，因此学得最深刻。写《Git 协作与分支管理规范》只花了半天，但规范若没有门禁和硬准入条件支撑，就只会停在纸面上——直到今天仓库仍是零提交、零 tag，无法用版本库佐证过程数据。配置管理的本质不是"用什么工具"，而是变更是否被记录、可回退、可追溯。 |
| **测试管理** | 测试不是开发的下游收尾，而是与设计并列的质量活动。107 条用例、4 轮执行、12 条缺陷的闭环让我明白：缺陷修复成本随发现时间急剧上升；边界值与等价类是最省钱的设计方法；没有自动化的回归资产是债务而非财富；缺陷趋势曲线收敛是一种可量化的交付信心。 |
| **文档规范** | 27 份文档按生存周期六阶段组织，每条需求可通过追溯矩阵双向追踪到设计、代码与用例。曾一度觉得"文档在为文档而写"，直到交叉校准时发现两份文档的用例数不一致，才明白文档集的价值恰恰在于自洽——一份文档可以含糊，一套自洽的文档不能。 |
| **团队协作与工程管理** | 工作量核算、责任矩阵、每日站会、里程碑准出检查单、变更委员会决策——这些看似行政性的工作，实际决定了 7 个人能否在 20 天内有序交付 5,929 行代码与 27 份文档。变更委员会一次会议驳回 28 人日的移动端需求，让团队理解了"做正确的事"比"多做一点"更重要。 |

## 9. 结项结论

本项目按"迭代式增量开发 + 原型驱动"过程模型执行，完成 SRS 全部 54 条功能需求（Must 级 34 条实现率 100%），25 条非功能需求中 21 条完成、3 条部分完成、1 条未完成且均有后续计划；6 个里程碑全部达成，累计提前 6 天交付；用例通过率 96.26%，无 Blocker 与 Critical 缺陷残留，缺陷修复率 91.67%；27 份文档齐备并通过核查。

**结项结论：项目目标达成，同意按计划结项并移交交付物；遗留事项 L-01、L-08 须在归档前关闭，其余遗留事项按版本计划跟踪闭环。**
