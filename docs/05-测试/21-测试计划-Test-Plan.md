## 1. 测试目的

本计划用于指导 SalesFlow CRM V1.0 的验证与确认活动，具体目的如下：

1. **验证功能正确性**：确认 SRS 中 54 条功能需求（FR-01 ~ FR-10）与 24 条非功能需求（NFR-P/U/R/S/M/T）均被正确实现，且实现结果与需求描述一致；
2. **验证业务规则精确性**：重点验证审批阈值（R1~R4 决策表）、商机阶段推进前置条件、回款状态判定规则、客户等级自动评定阈值等核心业务规则在边界取值上的行为是否符合 `app/src/config/businessRules.ts` 中的集中配置；
3. **验证 L2C 业务闭环**：通过端到端场景验证"线索 → 客户 → 商机 → 报价审批 → 合同订单 → 回款"全链路的数据贯通与状态机流转；
4. **验证权限模型**：验证四种角色（SALES / MANAGER / FINANCE / ADMIN）在菜单级、按钮级、数据行级三个维度的访问控制；
5. **发现并推动修复缺陷**：以分级、可追溯的方式管理缺陷，为验收决策提供量化依据；
6. **输出可验收证据**：形成测试用例集、缺陷记录与测试报告三份交付物，支撑课程项目验收与答辩演示。

## 3. 测试策略

### 3.1 测试级别与本项目落地方式

| 测试级别 | 标准定义 | 本项目落地方式 | 责任角色 | 产出 |
|---|---|---|---|---|
| **单元测试** | 对最小可测试单元（函数/方法）验证 | 不编写独立单元测试框架用例；以 **TypeScript 全量类型检查（`tsc --noEmit`）** 作为静态单元级质量门禁，覆盖类型契约与接口一致性（对应 NFR-M-03） | 开发负责人 | 类型检查报告 |
| **集成测试** | 验证模块间接口与数据流 | 以 **业务规则集中配置审查 + 跨模块数据贯通验证** 替代：审查 `businessRules.ts` 是否被组件硬编码绕过（NFR-M-01），并验证「报价→订单→回款计划」等跨模块数据流 | 测试工程师 + 开发负责人 | 代码审查记录、TC-NFR-017 |
| **系统测试** | 在完整系统上验证功能与非功能需求 | **本期主体**：107 条系统级用例，按 12 个模块组织，覆盖功能、边界、异常、权限、端到端与非功能 | 测试工程师 | 《测试用例集》SFS-CRM-TC-01 |
| **验收测试** | 由甲方/用户确认是否满足业务需求 | 以 SRS 7.2 主成功场景 10 步演示脚本为准，由甲方代表（课程指导教师）走查端到端主流程与关键报表 | 甲方代表 + 项目经理 | 《测试报告》SFS-CRM-TR-01 验收签字表 |

### 3.2 为什么以"手工功能测试为主 + 类型检查/构建为静态质量门禁"

本项目为**纯前端单页应用（Vite + React 18 + TypeScript + Tailwind CSS）**，无服务端、无对外 API、无并发与事务场景。基于这一事实，测试策略做如下取舍：

1. **自动化测试投入产出比低**：纯前端 + LocalStorage 的形态下，UI 自动化（E2E 工具）需额外引入浏览器驱动与测试运行环境，脚本维护成本高于其一次性验证价值；课程项目周期与人力约束下，将资源集中于业务规则与流程的正确性验证更具实效；
2. **业务逻辑高度集中在可审查的规则文件**：审批阈值、阶段赢率、等级阈值、回款分期模板全部集中在 `businessRules.ts`，一处人工核对即可覆盖多条用例的规则正确性，辅以类型检查可确保规则被正确引用；
3. **静态门禁可零成本拦截一类缺陷**：`tsc --noEmit` 全量类型检查 + `vite build` 构建通过，可在每次提交前零人工成本地拦截类型不匹配、未定义引用、枚举取值错误等静态缺陷，对应 NFR-M-03（TypeScript 全量覆盖，禁止 `any` 泛滥）与 NFR-T-03（构建产物为纯静态文件）；
4. **人工探索性测试更适合交互密集型系统**：看板拖拽、图表渲染、Toast 提示、二次确认弹窗等交互质量依赖人的主观判断，机器断言难以覆盖"提示是否明确""高亮是否醒目"等易用性判据；
5. **数据可重置保证可重复性**：LocalStorage + 一键重置演示数据（NFR-R-03）使每轮手工回归都能从确定的基线数据出发，弥补手工测试在可重复性上的不足。

**静态质量门禁定义**（每轮测试执行前必须通过，否则不予准入）：

| 门禁项 | 执行命令 | 通过判据 |
|---|---|---|
| 类型检查 | `npx tsc --noEmit` | 0 error |
| 生产构建 | `npm run build` | 构建成功，无 warning 级以上的编译错误 |
| 一键启动 | `npm install && npm run dev` | 全新环境可启动，首屏可访问 |
| 规则集中配置审查 | 人工审查 `src/**` 中是否出现 15%、30%、1000000、0.1/0.3/0.6 等硬编码字面量 | 无硬编码（TC-NFR-017） |

## 7. 缺陷分级标准

### 7.1 严重程度（Severity）

| 等级 | 定义 | 典型表现 | 处理时限 | 是否阻断准出 |
|---|---|---|---|---|
| **Blocker（致命）** | 系统崩溃、核心功能完全不可用、无规避方案、数据大面积损坏 | 无法登录；未登录可越权访问；主流程无法走通；数据全量丢失 | 立即（4 小时内响应，当日修复） | 是（残留 = 0） |
| **Critical（严重）** | 核心业务规则错误导致金额/统计口径失真，或关键数据不一致，影响经营决策 | 未确认回款计入已回款；审批链生成错误导致越权审批；金额计算错误 | 8 小时内响应，1 个工作日内修复 | 是（残留 = 0） |
| **Major（主要）** | 主要功能未实现或部分错误，但存在规避方案，不影响主流程走通 | 阶段推进前置条件未校验；必填校验缺失；过期报价仍可生成订单 | 1 个工作日内响应，2 个工作日内修复 | 残留 ≤1 且需规避方案 |
| **Minor（次要）** | 界面、文案、格式、易用性问题，不影响功能正确性 | 千分位缺失；逾期未高亮；提示文案不通顺；图表 tooltip 错位 | 2 个工作日内响应，本迭代内修复或登记延期 | 否（可遗留，需评估） |

### 7.2 优先级（Priority）

| 优先级 | 定义 | 与严重程度的对应关系 |
|---|---|---|
| **P1-紧急** | 必须立即修复，阻塞测试或演示 | Blocker、Critical 默认 P1 |
| **P2-高** | 本轮迭代必须修复 | Major 默认 P2；部分 Critical 视影响面可为 P1 |
| **P3-中** | 本迭代内安排修复，可延至下轮 | Minor 默认 P3 |
| **P4-低** | 可延期至后续版本 | 有规避方案的 Minor 可为 P4 |

### 7.3 缺陷状态流转

```
新建(New) → 已确认(Confirmed) → 已分配(Assigned) → 修复中(Fixing)
   → 待验证(Fixed) → 已关闭(Closed)
                          ↓ 回归未通过
                     重新打开(Reopened) → 修复中
   任意状态 → 已拒绝(Rejected) / 延期(Deferred)
```
