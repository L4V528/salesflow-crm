## 1. 编写约定

### 1.1 用户故事三段式

所有故事统一采用"角色—功能—价值"三段式表达，禁止只写功能不写价值：

> **作为**〈角色〉，**我希望**〈完成某项功能/动作〉，**以便**〈获得的业务价值〉。

示例：作为**销售员**，我希望**在客户详情页直接新建商机**，以便**不必在多个菜单之间来回切换，缩短从跟进到立项的时间**。

写作要求：

1. 角色必须来自 SRS 2.3 定义的四类角色之一（销售员 / 销售经理 / 商务财务 / 系统管理员），不写"用户"这一类泛化称呼；
2. "我希望"部分描述一个可交付、可演示的动作，而非技术实现（不写"我希望系统调用接口"）；
3. "以便"部分必须写出业务价值，价值需要可感知（缩短时长、减少错误、可追溯、可预测）；
4. 单个故事的开发工作量控制在 1 个 Sprint 内可完成，超出必须拆分。

### 1.2 INVEST 原则

| 字母 | 含义 | 本项目落地判据 |
|---|---|---|
| I | Independent 独立 | 故事之间尽量减少强依赖；确需依赖时在"依赖"列标注前置故事编号 |
| N | Negotiable 可协商 | 故事只描述"做什么"与"为什么"，实现细节在 Sprint 计划会上与开发协商 |
| V | Valuable 有价值 | 每条故事必须能映射到 SRS 的某条需求，并能回答"对谁有价值" |
| E | Estimable 可估算 | 故事须有明确的输入输出与验收标准，估算采用斐波那契数列 |
| S | Small 足够小 | 故事点 ≤ 8；超过 8 点必须拆分为多条 |
| T | Testable 可测试 | 每条故事至少 2 条验收标准，能以 Given/When/Then 表达 |

### 1.3 验收标准（AC）的 Given/When/Then 写法

验收标准统一采用三段式场景描述：

- **Given（前置上下文）**：描述系统处于什么状态、数据是什么、当前用户是谁；
- **When（触发动作）**：描述用户执行了什么操作；
- **Then（可观测结果）**：描述系统给出的确定响应（数据变化、界面变化、提示语、状态流转）。

约定：AC 至少 2 条、最多 4 条，其中必须包含一条**正向主场景**与一条**异常/边界场景**。为压缩篇幅，本文表格中简写为 `G … / W … / T …`，完整写法示例：

> **AC1（正向）**：**Given** 销售员张伟已登录且线索"华远科技"归属本人，**When** 他填写跟进内容并提交，**Then** 系统生成一条跟进记录，线索状态自动变为"跟进中"，详情页时间线置顶显示该记录。
> **AC2（异常）**：**Given** 跟进内容为空，**When** 点击提交，**Then** 提交按钮禁用且内容字段下方显示红色提示"跟进内容不能为空"。

### 1.4 估算与优先级口径

- **故事点（SP）**：斐波那契数列 1 / 2 / 3 / 5 / 8，1 点 ≈ 半天工作量（含自测）；5 点为中等复杂度（含多个校验分支），8 点为高复杂度（跨模块、含状态机或批量事务）；
- **优先级（MoSCoW）**：`Must` 不做则系统不可用；`Should` 重要但可延后一个 Sprint；`Could` 锦上添花，时间允许再做；`Won't` 本期明确不做（仅登记占位）；
- **Sprint 长度**：2 周（10 个工作日），团队规模 4 人，历史速度按 **50 SP/迭代** 规划。

### 4.5 待办维护规则

1. 每个 Sprint 开始前的计划会上重新估算与排序，MoSCoW 为 `Could` 的故事可随时下沉；
2. 迭代内新增需求须走 CRF 变更流程（SFS-CRM-CM-01），批准后插入待办并重新排期，原则上当期 Sprint 不接受范围外插入；
3. 故事状态流转：`待办 → 已排期 → 进行中 → 待验收 → 已完成`，仅当全部 AC 通过且演示通过后才允许置为"已完成"；
4. 燃尽图按日更新，连续两天无进展的故事须在每日站会上说明阻塞原因。
