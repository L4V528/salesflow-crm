## 1. 引言

### 1.1 编写目的

本报告从**技术、经济、操作、社会与法律**四个维度论证 SalesFlow CRM 项目的建设可行性，并通过三种备选方案的加权评分给出推荐结论，为项目立项决策提供依据。

### 1.2 背景

目标企业销售管理依赖 Excel + 微信群，存在线索流失、商机不可视、审批失控、回款脱节四类痛点（详见《项目立项建议书》SFS-CRM-PC-01 第 1.2 节）。本报告论证以自主建设方式交付 PC Web 端 L2C 全流程 CRM 的可行性。

### 2.2 前端框架选型：React vs Vue

| 比较维度 | 权重 | React | Vue 3 | 说明 |
|---|---|---|---|---|
| 团队熟悉度 | 0.15 | 5 | 4 | 团队 5/7 成员有 React 项目经验 |
| 生态与第三方库 | 0.15 | 5 | 4 | dnd-kit、React Router、ECharts 封装成熟 |
| TypeScript 支持 | 0.10 | 5 | 4 | React + TS 类型推导链更成熟 |
| 复杂状态与可维护性 | 0.15 | 4 | 4 | 双方均可满足，持平 |
| 招聘与知识沉淀价值 | 0.10 | 5 | 4 | React 在 B2B 中后台领域占有率更高 |
| 学习曲线 | 0.10 | 4 | 5 | Vue 单文件组件上手更快 |
| 拖拽/看板类方案成熟度 | 0.15 | 5 | 4 | dnd-kit 对 React 支持最完善 |
| 与 Tailwind 集成 | 0.10 | 5 | 5 | 持平 |
| **加权得分** | 1.00 | **4.80** | **4.20** | **选择 React** |

**结论**：选用 React。核心理由是本项目的看板拖拽（FR-05-01）、按钮级权限与复杂表单校验对第三方库依赖较强，React 生态在拖拽与中后台组件上方案最成熟；同时团队技术储备匹配度最高，可降低工期风险（对应风险 R-04）。

### 2.3 构建工具选型：Vite vs Webpack vs CRA

| 维度 | Vite | Webpack 5 | Create React App |
|---|---|---|---|
| 冷启动速度 | 毫秒级（ESM 原生按需编译） | 随项目规模线性增长，通常 10~30s | 慢（已停止维护推荐） |
| 热更新（HMR） | 模块级精准更新，< 100ms | 较快，但大项目回退 | 较慢 |
| 配置复杂度 | 极低，开箱即用 | 高 | 低但不可定制 |
| 生产构建 | 基于 Rollup，产物体积小 | 成熟，可深度优化 | 基于 Webpack |
| 维护状态 | 活跃 | 活跃 | **已废弃** |
| 对 NFR-T-02 支持 | 优（`npm run dev` 一键启动） | 良 | 良 |

**结论**：选用 **Vite**。本项目 26 天工期内迭代频繁，开发期的启动与热更新速度直接影响编码效率（约 45 人日编码工作量，按每日 30 次冷/热重载测算，每次节省 10~20 秒，全程可节省约 4~6 小时）；同时 Vite 天然输出纯静态产物，满足 NFR-T-03「可部署至任意静态服务器」。

### 2.4 样式方案选型：Tailwind CSS vs 其他

| 方案 | 开发效率 | 一致性 | 产物体积 | 定制成本 | 与 PC 中后台契合度 |
|---|---|---|---|---|---|
| **Tailwind CSS** | 高（无需切换文件、无需命名） | 高（设计令牌集中配置） | 小（Purge 后仅保留用到的类，通常 < 20KB） | 低 | **高** |
| CSS Modules | 中 | 中 | 中 | 中 | 中 |
| CSS-in-JS（styled-components） | 中 | 中 | 大（运行时开销） | 中 | 中 |
| 组件库（Ant Design） | 高 | 高 | **很大**（全量引入 1MB+） | 低 | 高 |
| 原生 CSS + BEM | 低 | 低 | 小 | 高 | 低 |

**结论**：选用 **Tailwind CSS**。理由有三：
1. **性能**：NFR-P-01 要求首屏 ≤ 2 秒，Tailwind 经 Purge 后 CSS 体积远小于组件库方案；
2. **一致性**：NFR-U-06/U-07 对金额格式、行高、密度有统一要求，Tailwind 通过 `tailwind.config.js` 集中定义间距与字号令牌，避免样式漂移；
3. **可控性**：本项目需要精细控制表格行高 ≤ 48px 等指标，原子类比组件库覆盖样式更直接，且不引入运行时开销。
> 组件库方面仅按需引入少量复杂组件（日期选择器、抽屉），避免全量引入。

### 2.5 数据持久化方案：LocalStorage vs 后端数据库

| 维度 | LocalStorage | IndexedDB | 后端数据库（MySQL + REST API） | 内存 Mock |
|---|---|---|---|---|
| 实现工作量 | **极低**（约 4 人日） | 中（8 人日） | 高（20+ 人日，含后端与部署） | 极低 |
| 容量上限 | 5MB | 数百 MB | 无实际限制 | 刷新即丢失 |
| 数据可靠性 | 浏览器级，清缓存/换机丢失 | 浏览器级 | 服务端持久化，可备份 | 无 |
| 多端共享 / 协同 | 不支持 | 不支持 | **支持** | 不支持 |
| 服务端鉴权 | 不可能（NFR-S-02 降级为演示级） | 不可能 | 真正安全 | 不可能 |
| 刷新不丢失（NFR-R-01） | **满足** | 满足 | 满足 | **不满足** |
| 一键重置演示数据（NFR-R-03） | 易实现 | 易实现 | 需后端脚本 | 天然满足 |
| 一键启动演示（NFR-T-02） | **满足** | 满足 | 需部署环境 | 满足 |
| 后续替换为 REST 的成本 | 已通过 Repository 抽象层隔离 | 已隔离 | — | 已隔离 |

**结论**：本期采用 **LocalStorage**，并以统一 Repository 接口封装数据访问层（SRS 6.2），未来替换 REST API 只需替换实现层、不改动业务组件。取舍逻辑如下：
- **本期核心目标是业务闭环演示与工程过程规范性**，而非生产级多用户协同，LocalStorage 以约 20% 的工作量覆盖 90% 的功能验证需求；
- 容量风险通过措施控制：演示数据约 0.6MB（远低于 5MB），写入前做容量预估，写入失败显式提示（NFR-R-02），提供 JSON 导出与一键重置（SRS 5.2、FR-10-04）；
- **必须承认的局限**：LocalStorage 无法实现真正的服务端鉴权与多端数据共享，故 SRS NFR-S-02 明确本期为"演示级实现，真实生产应由服务端鉴权"。该局限列入范围外（O-04）与 v2.0 规划，不作为本期验收项。

### 2.6 关键技术难点与预研结论

| 难点 | 对应需求 | 预研结论 | 处置 |
|---|---|---|---|
| 看板拖拽与阶段前置条件校验 | FR-05-01 | dnd-kit 支持拖拽生命周期钩子，可在 `onDragEnd` 中拦截并回滚 | 第 2 周技术预研（Spike），预留 3 人日 |
| 审批决策表与审批链动态生成 | FR-06-03 | 规则以配置表集中定义，审批链按规则动态构建 | 规则引擎配置化，禁止硬编码（NFR-M-01） |
| 金额精度（整数分存储） | SRS 2.5 | 全链路以整数分存储，展示层格式化 | 统一 money 工具函数 |
| 图表首屏性能 | NFR-P-01 | 图表组件懒加载 + 按需引入 | 路由级代码分割 |
| LocalStorage 写入失败 | NFR-R-02 | 捕获 `QuotaExceededError` 并提示 | 统一错误边界 |

**技术可行性结论**：所选技术栈均为成熟主流方案、开源许可友好、团队具备实施能力，关键技术难点已有明确解法并完成预研，**技术上完全可行**。

### 3.4 投资回收期与 ROI

| 指标 | 计算式 | 结果 |
|---|---|---|
| 一次性投入（内部口径） | 见 3.1 | 9.05 万元 |

**敏感性分析**：

| 情景 | 收益实现率 | 年化收益（万元） | 回收期 | 三年 ROI | 结论 |
|---|---|---|---|---|---|

## 4. 操作可行性

### 4.1 用户计算机水平评估

| 用户群 | 人数 | 现有技能 | 与本系统要求的差距 | 培训需求 |
|---|---|---|---|---|
| 销售员 | 8 | 熟练使用 Excel 与微信，日常使用浏览器；无 CRM 使用经验 | 需理解"商机阶段""审批流"等流程化概念 | 中（2 小时集中培训） |
| 销售经理 | 3 | 同上，具备报表阅读习惯 | 需掌握看板拖拽、批量分配、审批处理 | 中（2 小时） |
| 商务财务 | 2 | 熟悉财务软件与台账 | 需掌握商务审核、到账确认、开票登记 | 低（1 小时） |
| 系统管理员 | 1 | 具备基础 IT 运维能力 | 需掌握用户维护、产品目录、数据重置/导出 | 低（1 小时） |

评估结论：目标用户**均具备浏览器操作基础**，系统全部交互为 Web 表单、列表与按钮操作，无命令行、无安装步骤（`npm run dev` 一键启动，用户侧仅访问 URL），操作门槛低于用户现有 Excel 数据处理要求。

### 4.2 易用性设计对操作可行性的支撑

| SRS 易用性需求 | 对降低操作门槛的作用 |
|---|---|
| NFR-U-01 核心任务 3 次点击内进入 | 缩短操作路径，降低记忆负担 |
| NFR-U-02 破坏性操作二次确认 | 降低误操作恐惧，消除"不敢点"心理 |
| NFR-U-03 必填项精确标注 | 减少提交失败挫败感 |
| NFR-U-04 空/加载/错误状态明确提示 | 避免"页面空白不知怎么办" |
| NFR-U-05 操作成功/失败 Toast | 即时反馈，建立操作信心 |
| NFR-U-06 金额千分位、日期统一 | 与财务习惯一致，减少认知转换 |
| FR-01-03 四角色演示账号一键登录 | 培训与演示零门槛 |
| FR-10-04 一键重置演示数据 | 培训期可反复练习，无"练坏数据"顾虑 |

### 4.4 推广阻力分析与应对

| 阻力 | 表现 | 严重程度 | 应对措施 |
|---|---|---|---|
| 习惯依赖 | "Excel 用习惯了，为什么要换" | 中 | 上线首月双轨运行（Excel 台账与系统并行），用回款逾期预警等强感知功能建立价值认知 |
| 录入负担 | 认为录系统增加工作量，影响跑客户 | **高** | 表单必填项最小化（线索仅 5 项必填）；线索录入与跟进合并为一次操作；移动端录入列入 v2.0 |
| 数据透明顾虑 | 销售员担忧过程数据被管理层"监控" | **高** | 明确系统定位为"协同工具"而非"考核工具"；阶段留痕规则公开透明；考核口径与系统数据解耦，首月不挂钩绩效 |
| 管理层推动力不足 | 经理自身不使用，团队随之懈怠 | 中 | 经理侧专属价值（团队看板、加权预测、审批待办）优先交付；要求经理率先使用审批流 |
| 历史数据迁移顾虑 | 担心旧台账作废 | 低 | 明确历史数据不强制迁移（范围外 O-13），新业务自上线日起入系统 |

**操作可行性结论**：用户具备操作基础，系统设计已针对易用性做充分约束，培训成本低（3,000 元）、周期短（2 小时/场），主要推广阻力（录入负担、数据透明顾虑）均有明确应对措施。**操作上可行**。

## 5. 社会与法律可行性

### 5.1 个人信息保护合规（《个人信息保护法》）

系统处理的客户联系人信息（姓名、手机号、职务）属于《个人信息保护法》定义的**个人信息**，须遵守以下要求：

| 法条要求 | 系统现状与合规措施 | 对应设计 |
|---|---|---|
| 第五条 合法、正当、必要与诚信原则；最小必要 | 线索录入必填项仅 5 项（公司名称、联系人姓名、联系电话、来源渠道、意向等级），不采集身份证号、住址等敏感信息 | FR-03-01 |
| 第七条 公开处理规则、明示目的 | 系统仅在"建立与维护商业合作关系"目的内使用联系人信息，不做二次利用、不对外提供 | 数据保留规则（SRS 5.2） |
| 第十三条 取得同意 | 线索来源须填写来源渠道并留痕（展会名片、官网表单、转介绍等），作为取得同意的凭证 | FR-03-01 来源渠道必填 |
| 第十七条 告知义务 | 系统管理模块提供数据处理说明；线下获客场景由销售员履行告知 | 操作手册约定 |
| 第十九条 处理期限最小化 | 已废弃线索保留 24 个月后清理；逾期未成交线索可归档 | SRS 5.2 数据保留规则 |
| 第五十一条 安全技术措施（分类、加密、权限控制、教育培训） | ① 按角色分级访问控制（FR-01-04）；② 手机号在列表中默认脱敏展示（中间四位掩码）；③ 敏感操作记录操作人与时间（NFR-S-04） | FR-01-04、NFR-S-04 |
| 第四十七条 删除权 | 客户/联系人支持停用与归档；已转化线索因审计要求保留原始记录，但可申请去标识化处理 | SRS 5.2 |
| 第五十五条 个人信息保护影响评估 | 系统上线前完成一次数据合规自查，输出《数据合规自查表》 | 交付文档 |

**本期特有风险与缓解**：
1. **演示数据合规**：SRS 5.3 预置的 20 条联系人数据中，姓名与手机号**全部使用虚构数据**（手机号使用 `138-xxxx-xxxx` 保留号段格式但不指向真实个人），不涉及真实个人信息；
2. **鉴权强度不足**：本期为演示级前端鉴权（NFR-S-02），**如未来投入生产必须补做服务端鉴权**，否则无法满足第五十一条的安全技术要求；
3. **数据落地位置**：LocalStorage 数据存储于个人浏览器，不上传第三方，数据不出企业终端，客观上降低了外泄风险，但也带来设备丢失风险 —— 通过提供 JSON 导出与重置能力（FR-10-04）降低单点风险。

### 6.4 推荐结论

1. **评分最高**：加权总分 4.45，显著优于方案 B（2.90）与方案 C（2.25）；
2. **经济性最优**：三年总成本 12.65 万元，而方案 B 三年成本约 1.00 + 5.5×3 ≈ 17.5 万元，且支出为刚性、无资产沉淀；方案 A 形成可复用软件资产；
3. **业务贴合度**：本企业"15%/30%/100 万"三级折扣审批阈值、"三三四/全额预付/验收后付"分期模板属个性化规则，SaaS 标准产品需高价定制且难以完全匹配；
4. **数据自主**：客户与联系人是 B2B 企业核心资产，自研方案数据不出企业终端（LocalStorage）或自有服务器，规避第三方托管合规审查；
5. **教学目标**：本项目同时承担软件工程课程实训目标，自研是唯一能完整训练需求、设计、编码、测试、配置管理全流程的方案。
