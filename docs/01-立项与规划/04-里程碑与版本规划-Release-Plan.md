## 1. 版本策略

### 1.1 版本号规则

本项目采用**语义化版本（Semantic Versioning 2.0.0）**，版本号格式为：

```
vMAJOR.MINOR.PATCH[-PRERELEASE]
```

| 段位 | 升位条件 | 示例 |
|---|---|---|
| **MAJOR（主版本）** | 发生不兼容的架构变更、数据结构破坏性变更、对外接口不兼容变更 | `v1.x.x` → `v2.0.0`：引入后端 API 与真实数据库，数据结构重构 |
| **MINOR（次版本）** | 以向后兼容的方式新增功能模块或重要能力 | `v0.5.0` → `v0.9.0`：补齐数据看板与系统管理 |
| **PATCH（修订版本）** | 向后兼容的缺陷修复、文案与样式修正、性能微调 | `v1.0.0` → `v1.0.1`：修复回款逾期判定边界缺陷 |
| **PRERELEASE（预发布）** | 内测/候选版本标识，附加在版本号之后 | `v0.9.0-beta.1`、`v1.0.0-rc.1` |

### 1.2 本项目各版本段位的具体含义

| 版本段位 | 本项目中的具体判定标准 |
|---|---|
| **0.x.x（开发阶段）** | 课程建设期，未正式对外交付；允许数据结构与接口不兼容调整 |
| **1.x.x（正式交付）** | 通过甲方验收（M6），功能冻结并交付 27 份文档；此后仅做兼容修复 |
| **2.x.x（演进阶段）** | 引入服务端与数据库、移动端、消息推送等范围外能力（O-01 ~ O-04），涉及架构级变更 |

**tag 管理规则**

1. `main` 分支上的每个发布版本**必须**打附注 tag（`git tag -a vX.Y.Z -m "发布说明摘要"`）；
2. tag 命名必须与 `package.json` 的 `version` 字段严格一致；
3. tag 一经推送**不得移动或删除**，需修正时升 PATCH 版本；
4. 预发布 tag（`-beta.N`、`-rc.N`）在对应正式版发布后清理；
5. 每次打 tag 后 1 个工作日内由郑凯更新本表并升版本文档。

## 6. 后续 v2.0 规划

### 6.1 规划原则

v2.0 定位为**从"演示级单端应用"演进为"生产级协同系统"**，触发 MAJOR 升位（1.x → 2.0.0）。三条规划原则：**先补短板再扩功能**（优先解决服务端鉴权与数据持久化）；**按业务价值排序**（外勤效率与协同及时性优先）；**保持架构可演进**（延续 Repository 抽象层，替换实现层而非重写业务组件）。
