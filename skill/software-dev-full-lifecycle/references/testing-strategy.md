# 测试策略

> 本文是 `software-dev-full-lifecycle` Skill 的配套规范参考，供 AI 在 P4 测试阶段执行时遵循。内容对齐 SKILL.md 第 4 章（P4 测试）、铁律 5（一切可追溯）、反模式 7（测试只在最后做且只点主流程）。

测试的目标是"用证据证明系统做对了，并且做的是用户要的"。本文规定：测试级别、本项目"手工功能测试为主 + 静态门禁"的合理性、用例设计方法、缺陷分级与生命周期、测试报告与准出标准。

---

## 1. 测试级别

| 级别 | 验证对象 | 执行方式 | 本项目定位 |
| --- | --- | --- | --- |
| 单元测试 | 单个函数/组件 | 自动化（Vitest/Jest） | 业务规则函数（审批链、金额计算）必须单测 |
| 集成测试 | 模块协作/接口 | 自动化 + 手工 | 接口契约、Repository 与 DB 一致性 |
| 系统测试 | 完整系统功能 | 手工功能测试为主 | 本项目主战场，逐用例执行 |
| 验收测试 | 是否满足用户需求 | 用户/干系人参与 | 用端到端主成功场景演示 |

### 1.1 "手工功能测试为主 + 静态门禁"的合理性
本项目（教学/演示型 CRM）的特点：UI 交互多、后端可能为内存 Mock、变更频繁。因此：
- **静态门禁**（编译期保证）：TypeScript strict 类型检查零错误、构建通过、ESLint 无阻断项、业务阈值单测通过。这能在"不点界面"时就挡掉大量低级错误，对应 SKILL.md P3 Gate。
- **手工功能测试为主**：端到端业务流（线索→客户→商机→报价→订单→回款）依赖真实交互路径，自动化成本高、收益低，用手工用例集逐条执行更贴合"证明做对了"。
- 取舍说明：不追求 100% 自动化覆盖，但**所有 Must 需求必须有对应用例且通过**（P4 Gate 硬要求）。自动化只覆盖"易回归且高价值"的规则函数。

## 2. 测试用例设计方法

用例字段统一（SKILL.md 4.1）：`编号 | 模块 | 标题 | 前置条件 | 步骤 | 测试数据 | 预期结果 | 优先级 | 关联需求 | 实测结果`。五类覆盖：正向 / 反向异常 / 边界 / 权限 / 端到端。

### 2.1 等价类划分
把输入域分成"有效等价类"和"无效等价类"，每类取一个代表值，减少用例数。
- 例：折扣率输入域，有效类 [0,1]，无效类 <0 与 >1。只需各取代表（如 0.2 / -0.1 / 1.5）。

### 2.2 边界值分析（阈值类规则尤其重要）
边界点取"正好边界、边界±1 单位"。SKILL.md 明确指出折扣阈值 15%、30% 要设计 14.9%、15.0%、29.9%、30.0% 四点；金额 50 万同理取 49.9 万、50.0 万。
- 规则：若输入条件为"a ≤ x ≤ b"，取 a-、a、a+、b-、b、b+ 六点（或边界±邻域）。
- 对**整数分**金额，边界用分单位算（4,999,999 / 5,000,000 / 5,000,001 分）。

### 2.3 场景法（端到端）
以业务流为主线设计场景：主成功场景 + 备选场景 + 异常场景。
- 主成功：线索转化→建客户→建商机(赢单)→建报价(审批通过)→建订单(付款)→回款(结清)。
- 备选：报价被驳回→修改→再提交。
- 异常：审批超时、并发修改、网络中断后重试。

### 2.4 状态转换测试
针对状态机对象（商机/报价/订单/回款），对每个合法转换设计用例，并验证**非法转换被拒**。
- 覆盖矩阵：行=源状态，列=事件，格=期望目标（含"非法"标记）。
- 例：报价"已通过"状态再点"提交审批"应被拒并提示。

### 2.5 权限矩阵测试
按 SKILL.md 权限模型（角色→菜单→按钮→数据范围）逐格验证：
| 角色 | 商机创建 | 报价审批 | 查看他人数据 |
| --- | --- | --- | --- |
| 销售员 | ✓ | ✗ | 仅本人 |
| 销售总监 | ✓ | 单级 | 本团队 |
| 总经理 | ✓ | 两级 | 全公司 |
每个"✓/✗"格至少一条用例，验证越权被拦。

## 3. 缺陷分级与生命周期

### 3.1 缺陷分级
| 级别 | 定义 | 处理时限 | 示例 |
| --- | --- | --- | --- |
| Blocker | 系统不可用/数据丢失/无法部署 | 立即 | 部署后白屏、回款金额算错 |
| Critical | 核心功能错误，无变通 | 24h | 审批链错误导致越权通过 |
| Major | 主要功能缺陷，有变通 | 本迭代 | 列表分页错、导出缺列 |
| Minor | 界面/文案等次要问题 | 可排期 | 按钮错位、提示文案错别字 |

### 3.2 生命周期
```
发现 → 提交(带根因分析) → 确认 → 分配 → 修复 → 验证 → 关闭
```
- 缺陷单必须写**根因分析**，不是只描述现象（SKILL.md 4.2）。例：根因=审批状态未回退草稿，因驳回分支漏调 `revertToDraft()`。
- 修复后由非提交人验证，验证用例与原用例一致。
- 关闭前回填 RTM 中对应用例状态。

## 4. 测试报告与准出标准

### 4.1 测试报告必备内容（SKILL.md 4.3）
- 用例执行率 = 已执行/总用例 ×100%
- 通过率 = 通过/已执行 ×100%
- 按模块分布（哪模块缺陷多）
- 缺陷分布与修复率（各级别数量、已修/未修）
- 遗留缺陷影响评估（Minor 遗留是否可接受）
- **非功能需求逐条验证结论**（NFR 是否达标）
- 准出结论（Go / No-Go）

### 4.2 准出标准（P4 Gate 硬门槛）
- 用例执行率 **100%**
- 通过率 **≥ 95%**
- **无 Blocker / Critical 残留**
- 每条 Must 需求有对应用例且通过

### 4.3 与 RTM 的闭环
测试报告中的"关联需求"列必须能回指 RTM；未通过用例的需求在 RTM 标记"已实现未验/未通过"，禁止标记为"已闭环"。这正是铁律 5"任何一条需求没有对应测试视为未完成"的落地。
