# 设计与架构规范

> 本文是 `software-dev-full-lifecycle` Skill 的配套规范参考，供 AI 在 P2 系统设计阶段执行时遵循。所有内容对齐 SKILL.md 第 2 章（P2 系统设计）与铁律 2（决策先于实现）、4（业务规则集中）、5（一切可追溯）。

设计阶段把 SRS 翻译成可实现的蓝图。本规范要求：**架构分层与依赖方向、ADR 决策记录、数据建模取舍、接口契约、UI 规范**。所有设计必须能回指到具体需求编号（RTM 的"设计模块"列）。

## 1. 分层架构

### 1.1 四层模型
```
表现层(Presentation)  →  业务层(Business/Service)  →  数据访问层(Repository)  →  持久化层(DB)
```
- **依赖方向只能向下**：表现层依赖业务层，业务层依赖数据访问层，数据访问层依赖持久化层。禁止反向依赖（如业务层 import 页面组件）、禁止跨层调用（页面直接写 SQL）。
- 前端典型分层：页面/路由 → 容器组件(连接状态) → 展示组件(纯 UI) → 服务/API 客户端 → 领域模型/工具。

### 1.2 前端常见架构模式
| 模式 | 适用 | 要点 | 风险 |
| --- | --- | --- | --- |
| MVC | 传统服务端渲染 | Model 数据、View 视图、Controller 路由 | 控制器易膨胀 |
| MVVM | 数据驱动 UI（React/Vue） | ViewModel 绑定，状态自动映射视图 | 大型 VM 难维护 |
| 组件化 | 现代 SPA 标配 | 原子→分子→页面逐级组合 | 过度拆分反而难读 |
| 状态管理选型 | 跨页共享状态 | 轻量用 Context/Zustand，复杂用 Redux | 把本属本地状态塞进全局 |

**状态管理选型建议**：仅"跨多个不相邻组件、需持久化、需审计"的状态进全局；表单草稿、弹窗开关等局部状态留在组件内。避免"全局仓库变成第二个数据库"。

### 1.3 依赖方向原则（铁律 4 落地）
- 业务规则集中在 `config` / `domain` 层，组件与页面不得内含阈值判断。
- 接口契约（类型定义）由数据访问层/data 层向外暴露，调用方依赖接口而非实现。
- 通用工具（日期、金额格式化）下沉到 `shared/utils`，禁止各组件各写一份。

## 2. ADR（架构决策记录）

最有价值的架构文档内容（SKILL.md 要求至少 5 条）。ADR 记录"为什么这么定"，让后人不用猜。

### 2.1 模板
```
# ADR-<编号> <标题>
## 状态 Status
  已采纳 / 已废弃 / 待定（含 superseded-by 指向）
## 背景 Context
  面临什么问题、有哪些约束（性能/工期/团队能力/合规）
## 决策 Decision
  我们决定采用……
## 理由 Rationale
  为什么这样选：权衡了哪些方案、放弃了什么
## 后果 Consequences
  正面：……  负面/代价：……  后续待办：……
## 关联需求
  FR-x-y / NFR-x-y
```

### 2.2 示例
```
# ADR-03 报价审批链采用配置驱动而非硬编码
## 状态  已采纳
## 背景  折扣率阈值、审批层级未来可能随组织调整变化
## 决策  审批层级与阈值写在 approval.config.ts，由规则引擎读取
## 理由  避免"改一处漏三处"（反模式 3）；业务人员可自运维
## 后果  正面：变更无需改代码  负面：需额外写规则校验单测
## 关联  FR-3-01, BR-QUOTE-APPROVAL
```

至少覆盖的 5 类决策：技术栈选型、架构分层方式、状态管理选型、数据持久化方案、权限模型、外部集成方式。

## 3. 数据建模

### 3.1 ER → 表
- 每个实体→一张表，弱实体加父外键；M:N 关系→中间表。
- 命名：表 `t_模块_实体`（如 `t_sale_quotation`），字段小写下划线，主键 `id` 或 `实体_id`。

### 3.2 范式与反范式取舍
- 默认满足 3NF（消除传递依赖），保证写入一致。
- **反范式仅在**高频只读、联表代价高时采用（如报表宽表冗余客户名）。反范式须显式写 ADR 说明理由，并标注"冗余字段，由 X 事件同步"。

### 3.3 状态字段设计
- 状态用**枚举字典集中定义**（`shared/constants/status.ts`），禁止散落字符串。
- 状态字段加 `status` + `status_updated_at`；跨状态须配状态机（见需求工程状态图）。

### 3.4 快照策略
- 报价单的"折扣率/金额"在审批通过后应**快照**，防止客户主数据被改后历史报价失真。
- 审计数据（审批记录、操作日志、状态历史）**禁止物理删除**（铁律/反模式对应），用 `deleted_at` 软删或仅追加。

### 3.5 金额与精度（铁律 4 衍生）
- 所有金额以**整数分**存储与计算（`amount_cents: number`），禁止裸 `float` 参与计算（0.1+0.2≠0.3）。展示层再除 100 格式化。
- 币种、精度在领域模型中统一，避免各页各自四舍五入。

## 4. 接口设计

### 4.1 REST 契约
- 资源用名词复数：`GET /api/quotations`、`POST /api/quotations/{id}/approve`。
- 契约文档写清：方法、路径、入参（类型+必填）、返回结构、前置条件、**失败场景与错误码**。
- 分页/排序统一：`?page=1&size=20&sort=created_at,desc`。

### 4.2 Repository 接口
业务层只依赖 Repository 接口（如 `QuotationRepository.findPending()`），不关心实现是内存还是数据库。便于测试替身与切换存储。

### 4.3 错误码设计
统一结构：
```json
{ "code": "QUOTE_001", "message": "折扣率超出权限，需上级审批", "details": null }
```
- 错误码分层：`MODULE_ACTION_SEQ`；用户可读 `message` 与机器码 `code` 分离。
- 业务校验失败返回 4xx + 明确文案；系统异常返回 5xx + 追踪号，不向用户暴露堆栈。

## 5. UI / 交互设计规范要点

对齐 SKILL.md 2.4（UI 与原型）。

| 维度 | 规范要点 | 反模式 |
| --- | --- | --- |
| 信息密度 | 列表页一屏可见核心字段，次要字段折叠/详情 | 一屏塞 30 列导致找不到重点 |
| 状态可见性 | 每个异步操作有 loading/成功/失败三态反馈 | 写入失败静默，用户不知成败 |
| 防错 | 破坏性操作二次确认；必填与格式前端即时校验 | 删数据无确认，误删不可恢复 |
| 一致性 | 同义操作按钮位置/文案统一；空态/错误态有图有文 | 同功能三处三种叫法 |
| 可达性 | 关键操作键盘可达、对比度达标 | 仅鼠标可点的隐藏菜单 |

原型验证：走查 + 可用性测试 + 问题分级，回流到需求（反模式 9 对应，不隐藏已知限制）。
