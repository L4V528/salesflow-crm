# 需求工程规范详解

> 本文是 `software-dev-full-lifecycle` Skill 的配套规范参考，供 AI 在 P1 需求工程阶段执行时遵循。所有规则与 `SKILL.md` 六条铁律一致：阶段不可跳跃、文档先于代码、不懂就问、业务规则集中、一切可追溯、变更受控。

需求工程是整个流程的"重中之重"。需求若含糊、遗漏或自相矛盾，后续设计、编码、测试的全部投入都会打水漂。本文规定：**需求如何分类、怎样算一条好需求、用什么方法表达、如何编写 SRS、如何评审与基线化**。

---

## 1. 需求分类

一条需求不是"一句话想法"，而是分层的。按抽象级别与关注点，分为六类。任何项目都至少要识别出功能需求、非功能需求、数据需求、接口需求；业务需求与用户需求用于向上对齐目标。

| 类别 | 关注点 | 回答的问题 | 例子（CRM 销售管理） |
| --- | --- | --- | --- |
| 业务需求 | 组织级目标、投资回报 | 为什么要做这个系统？ | 报价审批周期从 3 天缩短到 1 天，商机转化率提升 15% |
| 用户需求 | 角色视角的诉求 | 某类用户想借助系统达成什么？ | 销售员希望手机端提交报价后实时看到审批进度 |
| 功能需求 | 系统必须做什么 | 系统应提供哪些可操作能力？ | 系统应支持对报价单发起两级审批（FR-3-02） |
| 非功能需求 | 系统做得"多好" | 性能/安全/易用等质量约束？ | 报价列表查询响应 ≤ 1.5 秒（NFR-P-01） |
| 数据需求 | 数据如何存、留、保护 | 实体、量级、保留期、隐私？ | 商机数据自关闭起保留 3 年，审计记录不可删除 |
| 接口需求 | 与外部的边界 | 与谁对接、怎么对接？ | 通过 REST 调用企业微信审批回调接口 |

**易错点**：把"业务需求"误写成"功能需求"。例如"提升转化率"是业务需求，不是功能需求，它不能直接写测试用例。功能需求必须可映射到具体页面/接口/操作。

## 2. 需求质量特征（八维）

SKILL.md 要求"每条需求满足正确性、无歧义、完整性、一致性、可验证性、可追踪性、必要性、有优先级"。逐条解释与自检方法：

| 特征 | 含义 | 自检提问 | 反例（不合格） |
| --- | --- | --- | --- |
| 正确性 | 真实反映用户意图 | 这条是用户真的要的吗？ | "系统应支持 5 级审批"（用户实际只要 2 级） |
| 无歧义 | 只有一种解释 | 两个评审人读出的意思一致吗？ | "系统应尽快处理"（多快算快？） |
| 完整性 | 不缺前置/输入/输出/异常 | 输入、处理、输出、异常都写了吗？ | "系统应生成报表"（何时生成？格式？） |
| 一致性 | 不与其它需求冲突 | 与 FR-xx、NFR-xx 矛盾吗？ | 一处写"金额用元"，一处写"金额用分" |
| 可验证性 | 能设计测试证明满足 | 存在可测量的验收标准吗？ | "系统应易用"（无法量化验证） |
| 可追踪性 | 有唯一编号可追溯 | 编号唯一且能挂到 RTM 吗？ | 散落在段落里没有编号 |
| 必要性 | 不做会损害目标 | 删掉它系统还能达标吗？ | "支持 12 国语言"（本期无此需要） |
| 优先级 | 用 MoSCoW 标注 | Must/Should/Could/Won't？ | 全部标 Must（等于没排序） |

**MoSCoW 用法**：Must（本期必须，无则不可交付）、Should（重要但可妥协）、Could（有最好）、Won't（本期不做，记录以防遗忘）。Gate 检查只硬性要求"全部 Must 需求有验收标准且被覆盖"。

## 3. 建模表达方法详解与应用场景

纯自然语言无法表达复杂逻辑。下表是 SKILL.md 1.2 表的展开版，给出每种方法的**画法要点**与**何时必用**，AI 在建模时应直接产出对应图/表。

### 3.1 用例图（Use Case Diagram）
- 元素：参与者（小人）、用例（椭圆）、系统边界（方框）、关联/包含(«include»)/扩展(«extend»)关系。
- 要点：只画"系统对外提供的价值"，不画内部步骤；«include» 表示必走子流程（如"登录"），«extend» 表示可选扩展（如"导出异常报告"）。
- 必用：任何项目必做，作为功能边界总览。

### 3.2 用例规格说明（Use Case Specification）
结构化模板，每个核心用例一份：

| 字段 | 内容 |
| --- | --- |
| 用例编号 | UC-商机-01 |
| 基本流（Happy Path） | 1.销售新建商机 2.填写客户/金额 3.保存 4.系统生成商机编号 |
| 备选流 | 2a.客户不存在→先建客户再返回 |
| 异常流 | 3a.必填缺失→提示并返回；4a.并发冲突→提示"数据已被修改" |
| 前置条件 | 已登录且具"商机创建"权限 |
| 后置条件 | 商机状态=草稿，写入操作日志 |

基本流写"正常怎么走"，备选流写"用户合法但走了别的分支"，异常流写"系统或输入出错怎么办"。**异常流是演示防破的关键**。

### 3.3 用户故事 + 验收标准（AC）
- 格式：`作为<角色>，我想要<能力>，以便<价值>`。
- AC 写法一 INVEST（故事本身质量）：Independent 独立、Negotiable 可协商、Valuable 有价值、Estimable 可估算、Small 够小、Testable 可测。
- AC 写法二 GWT（Given-When-Then）：
  - Given 一个折扣率 35% 的报价单
  - When 销售提交审批
  - Then 系统触发"销售总监+总经理"两级审批链
- 必用：敏捷型项目必做；每条用户故事须有 GWT 形式的 AC，否则不可进入迭代。

### 3.4 活动图 / 流程图
表达业务流程与分支、并行。必用于有审批流/多分支流程（如报价审批：提交→判断折扣率→单级或两级→通过/驳回）。用泳道（Swimlane）区分角色职责。

### 3.5 状态机（状态图）
表达实体生命周期。必用于有状态对象：商机（草稿→跟进中→赢单/输单）、报价（草稿→审批中→已通过/已驳回）、订单（待付款→已付款→已发货→已完成/已取消）、回款（待回款→部分回款→已结清）。
每个转换必须写清：**源状态、触发事件、守卫条件、目标状态、动作**。例如 `审批中 --[折扣率<30% 且 总监通过]--> 已通过`。

### 3.6 数据流图 DFD
分层（Context→Level 0→Level 1）表达数据加工与流动。数据处理类系统必用。元素：外部实体、加工、数据存储、数据流。注意只画数据，不画控制流。

### 3.7 ER 图 / 领域模型
- ER 图：实体、属性、主外键、关系基数（1:1 / 1:N / M:N）。
- 领域模型：在 ER 基础上附加聚合、值对象、领域事件（DDD 视角）。
- 必用：任何有持久化的项目必做。线索/客户/商机/报价/订单/回款在 CRM 中构成核心领域模型。

### 3.8 时序图
表达对象间消息时序。多系统/多模块协作必用（如"前端→API 网关→审批服务→企业微信→回调"）。标注每个消息的同步/异步与返回。

### 3.9 决策表
表达"条件组合→动作"。规则型需求必用，如折扣审批阈值：

| 条件/动作 | 规则1 | 规则2 | 规则3 | 规则4 |
| --- | --- | --- | --- | --- |
| 折扣率 < 15% | Y | - | - | - |
| 15% ≤ 折扣率 < 30% | - | Y | - | - |
| 折扣率 ≥ 30% | - | - | Y | Y |
| 金额 < 50 万 | - | - | Y | - |
| 金额 ≥ 50 万 | - | - | - | Y |
| 动作：销售总监审批 | ✓ | ✓ | | |
| 动作：总经理加签 | | | ✓ | ✓ |

"Y/空白/-"分别表示真/假/无关。决策表能暴露"漏组合"（如某区间无规则覆盖）。

### 3.10 原型
界面与交互的快速可见物。分抛弃式（验证想法，用完即弃）与演化式（即产品骨架，持续演进）。有 UI 项目必做，至少覆盖核心 3~5 个页面。

### 3.11 需求追踪矩阵 RTM
贯穿全周期的追溯骨架，字段：`需求编号 | 需求简述 | 来源(访谈/原型) | 用例 | 设计模块 | DB表 | 页面 | 测试用例 | 状态(新增/已实现/已验)`。需求一旦入 RTM，即为"已纳入管控"。

## 4. 需求基线、评审与 SRS

### 4.1 需求基线
SRS 达到 v1.0 后**冻结**，后续改动一律走变更流程（见 SKILL.md 1.5）。版本演进：`v0.1 草稿 → v0.5 内部评审 → v0.9 评审稿 → v1.0 基线`。基线前后任何差异必须可查。

### 4.2 需求评审三种形式
| 形式 | 适用 | 要点 |
| --- | --- | --- |
| 走查（Walkthrough） | 作者讲解，团队提意见 | 轻量，早期用 |
| 审查（Inspection） | 正式，角色分工（主持/讲解/记录/评审员） | 带检查单，产出缺陷清单 |
| 技术评审（Technical Review） | 跨职能确认技术可行性 | 架构/测试代表必到 |

评审必须产出**待定问题清单（Q-01、Q-02…）**，承认不确定性。例如 Q-01："折扣率≥30% 是否还需要财务复核？待财务总监确认。"——这比假装确定更专业。

### 4.3 SRS 标准目录（GB/T 9385 / IEEE 830 对齐）
1. 引言（目的、范围、术语定义、参考文献）
2. 总体描述（产品前景、用户特征、运行环境、约束、假设依赖）
3. 功能需求（逐条 FR-x-y：输入/处理/输出/业务规则/异常）
4. 非功能需求（NFR：性能/易用/可靠/安全/可维护/可移植，逐条可测）
5. 外部接口需求（用户/软件/通信接口）
6. 数据需求（实体、保留规则、量级）
7. 其他需求（验收标准、端到端主成功场景、约束与风险）
8. 附录（用例清单、术语表、修订历史）

### 4.4 需求条目化写法示例（正例 vs 反例）
反例（违反"可验证性/完整性"）：
> FR-3-01 系统应支持报价审批功能。

正例（符合八维）：
> **FR-3-01 报价审批**
> - 输入：报价单（含折扣率、金额）、审批人意见
> - 处理：提交时按决策表 BR-QUOTE-APPROVAL 判定审批链；折扣率≥30% 或金额≥50 万触发两级审批
> - 输出：生成审批任务，通知审批人；结果写入审批记录
> - 业务规则：BR-QUOTE-APPROVAL（见决策表）；任何审批节点驳回则报价回退"草稿"
> - 异常：审批人 48h 未处理系统自动提醒一次；审批中报价不可编辑
> - 验收标准：构造折扣率 35%、金额 60 万报价，提交后须出现"销售总监→总经理"两级任务
> - 优先级：Must
